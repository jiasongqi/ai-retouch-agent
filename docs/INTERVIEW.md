# 面试题解

围绕本仓库真实设计回答。先说结论，再补实现位置。想顺着代码学，用 [学习笔记](learn/README.md)。

## 1. 这和「聊天框里出一张图」有什么区别？

结论：这是带计划、工具、画布状态的 Agent 工作台，不是单次文生图。

用户一句话会变成多步 JSON 计划（抠图 → 换背景 → 导出）。每一步对应注册表里的工具，作用在图层文档上，进度经 SSE 推到前端。用户可以确认计划、单步重试或取消。

## 2. 为什么用 LangGraph，而不是一次 LLM 调用？

结论：修图是有依赖的多步任务，需要状态图把「规划」和「校验」拆开。

`backend/app/agent/graph.py` 里先 `_plan` 让模型产出 `tool_calls`，再 `_verify` 走 `validate()`。模型不能直接改像素。校验失败则清空计划并返回可读原因。

## 3. 为什么模型给出的计划不能直接执行？

结论：模型会编造工具名、漏参数、把步骤接成环。

`backend/app/agent/plan.py` 做存在性、参数、依赖补全、环检测和拓扑排序。未知工具抛 `UnknownTool`，参数不合法抛 `InvalidParams`。这是 Agent 落地时最常被问的「护栏」。

## 4. UI 按钮和 Agent 会不会各写一套接口？

结论：不会。26 个工具登记在 `backend/app/tools/__init__.py` 的 `SPECS`。

`spec_of(name)` 给执行路径用，`label_of` 给界面文案用。新增工具只改注册表；Agent 若需主动选用，再补系统提示。面试时可以对比「Function Calling 散落在各页」的坏味道。

## 5. 图层和选区为什么要分开？

结论：图层回答「改哪一层」，选区回答「改哪一块」。

用户说「把物体 2 变红」应填 `layer_id`，走 `replace_region`；整张换背景才用 `replace_background`。画布已有选区时，局部消除 / 替换 / 提升为图层直接用该选区，不要让用户再点一次。系统提示里把这条写死，减少规划漂移。

## 6. 进度怎么到浏览器？任务为什么不放在 API 进程里跑？

结论：修图像素计算和模型调用耗时长，API 只负责接请求；ARQ Worker 执行，Redis Pub/Sub 发进度，前端 SSE 订阅。

好处：刷新页面不丢任务、多步可恢复、API 不会被一张超分堵住。注意 EventSource 不能自定义 Header 时，鉴权策略要和 cookie / ticket 设计一致。

## 7. `IMAGE_PROVIDER=mock` 解决什么问题？

结论：把「系统能不能跑通」和「模型好不好」分开。

Provider 抽象在 `backend/app/providers/`。mock 返回占位图，pytest 和本地演示不消耗额度。切 `dashscope` 只换实现，工具协议不变。这是可测试 Agent 的标准说法。

## 8. 平台主图为什么不用 `crop_canvas`？

结论：硬裁会切掉主体，也不满足各平台安全区和占比。

`prepare_platform_export` / `prepare_delivery_sizes` 按画幅和主体占比放置（淘宝主图、亚马逊主图、抖音封面等）。一键套图 `export_listing_pack` 一次出白底、场景、卖点、9:16。场景库是本地合成，不是再调一次文生图碰运气。

## 9. 如何保证计划里的依赖顺序是对的？

结论：步骤默认依赖前一步；服务端拓扑排序，发现环就拒绝执行。

面试可补：并行无依赖步骤可以同时跑，但像素写入同一画布时要避免写冲突——本项目以拓扑后的串 / 按依赖执行为主，简单、可推理。

## 10. 如果让你继续做，下一步是什么？
